# API (Buyer) — Draft / Internal

This document describes the current buyer-facing HTTP API as implemented in this repo. It is intentionally practical and may change as stabilization continues.

Base URL: `http(s)://<host>`

All buyer endpoints are under: `/api/v1/*`

## Authentication

Buyer endpoints require `Authorization: Bearer <token>`.

Supported bearer token formats:
- JWT access token from `/auth/login` or `/auth/register`
- Managed API key token generated by `/api/v1/api-keys`
- Legacy single API key token generated by `/api/v1/api-key/regenerate`

Notes:
- The backend uses the same `Authorization: Bearer ...` header for both JWT and API key.
- If you send an invalid token/key, you will get `401` with a JSON error `{"detail": "..."}`.

### Register / Login (JWT)

`POST /auth/register`
- Creates a user, wallet, and default limits.

`POST /auth/login`
- Returns access + refresh token.

`POST /auth/refresh`
- Returns new access + refresh token.

### API keys (optional)

`POST /api/v1/api-keys`
- Requires JWT auth.
- Returns a new raw API key once.
- Stores only a hash and display prefix.

Body:
```json
{
  "name": "local dev key",
  "scopes": {
    "orders": "read_write"
  }
}
```

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/api-keys" \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{"name":"local dev key"}'
```

`GET /api/v1/api-keys`
- Requires JWT auth.
- Lists current user's keys.
- Does not return raw keys or key hashes.

`POST /api/v1/api-keys/{public_id}/revoke`
- Requires JWT auth.
- Idempotently revokes one of the current user's keys.

`GET /api/v1/api-keys/{public_id}/usage`
- Requires JWT auth.
- Returns usage visibility for one of the current user's managed API keys.
- Includes total request count, `last_used_at`, and grouped recent counts by endpoint/method/status.
- Does not expose raw keys, key hashes, or request IP addresses.

Scopes are stored for future enforcement but are not enforced yet.

### Legacy API key

`POST /api/v1/api-key/regenerate`
- Requires JWT auth (buyer user).
- Returns a new API key once. Store it; it is not shown again.
- Legacy compatibility endpoint. Prefer `/api/v1/api-keys` for new integrations.

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/api-key/regenerate" \
  -H "Authorization: Bearer $JWT"
```

## Payment Intents (Deposit Foundation)

`POST /api/v1/payment-intents`

Headers:
- `Authorization: Bearer <token>`
- `Idempotency-Key: <string>` (optional, recommended)

Body:
```json
{
  "amount": "10.0000",
  "provider": "manual_test",
  "currency": "USD"
}
```

Current provider behavior:
- Allowlist: `manual_test`, `payme`, `click`, `crypto_usdt`
- Enabled now: `manual_test` only

Important:
- Creating a payment intent does not credit wallet balance yet.
- Internal payment webhooks can update payment intent status.
- When an internal webhook transitions a payment intent to `succeeded`, the wallet is credited once with a `deposit` wallet transaction.
- Real payment provider verification/signature integrations are not implemented yet.

Idempotency behavior:
- Same user + same key + same request body returns the same payment intent.
- Same user + same key + different body returns `409`.
- Different users can reuse the same key.

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/payment-intents" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: pay-intent-1" \
  -H "Content-Type: application/json" \
  -d '{"amount":"10.0000","provider":"manual_test","currency":"USD"}'
```

`GET /api/v1/payment-intents/{public_id}`

- Returns only the authenticated user's own payment intent.

Response fields:
- `public_id`
- `provider`
- `currency`
- `amount`
- `status`
- `expires_at`
- `created_at`

## Wallet Transaction History

`GET /api/v1/wallet/transactions`

Query params:
- `limit` (default 100, max 500)
- `offset` (default 0)

Response items include:
- `id`
- `type` (`deposit`, `adjustment`, `hold`, `capture`, `refund`)
- `amount`
- `status`
- `order_public_id` (nullable)
- `reference` (nullable)
- `created_at`

Notes:
- This endpoint returns only the authenticated user's transactions.
- It does not expose internal provider/supplier cost fields.
- Successful payment intents appear as `deposit` transactions with no linked order.

Example:
```bash
curl -sS "$BASE_URL/api/v1/wallet/transactions?limit=50&offset=0" \
  -H "Authorization: Bearer $TOKEN"
```

## Catalog: Services, Countries, Prices

`GET /api/v1/services`
- Returns active services.

`GET /api/v1/countries`
- Returns active countries.

`GET /api/v1/prices`
Query params:
- `service_code` (optional)
- `country_iso2` (optional, 2-letter ISO2)

Response items include (current fields):
- `service_code`, `country_iso2`, `operator` (nullable)
- `provider_code`, `provider_name` (nullable)
- `final_price`
- `available_count`
- `delivery_rate`

Important:
- Internal cost fields (e.g. provider margin inputs) are not exposed in buyer price responses.

Example:
```bash
curl -sS "$BASE_URL/api/v1/prices?service_code=telegram&country_iso2=ID" \
  -H "Authorization: Bearer $TOKEN"
```

## Orders

### Create order (with optional idempotency)

`POST /api/v1/orders`

Headers:
- `Authorization: Bearer <token>`
- `Idempotency-Key: <string>` (optional)

Body:
```json
{
  "service_code": "telegram",
  "country_iso2": "ID",
  "operator": null
}
```

Idempotency behavior:
- If `Idempotency-Key` is omitted: normal behavior (each request can create a new order).
- If `Idempotency-Key` is provided:
  - Same user + same key + same body returns the same order response.
  - Same user + same key + different body returns `409`.

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/orders" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: my-client-key-123" \
  -H "Content-Type: application/json" \
  -d '{"service_code":"telegram","country_iso2":"ID","operator":null}'
```

Successful response (shape):
- `public_id`
- `service_code`, `country_iso2`, `operator`
- `phone_number` (nullable; usually present after reservation succeeds)
- `status` (string)
- `price`
- `sms_code` / `sms_text` (nullable until received)
- `expires_at`, `created_at`, `updated_at`

### Get order

`GET /api/v1/orders/{public_id}`

Example:
```bash
curl -sS "$BASE_URL/api/v1/orders/$PUBLIC_ID" \
  -H "Authorization: Bearer $TOKEN"
```

### List orders

`GET /api/v1/orders`
Query params (all optional):
- `status`
- `service`
- `country`

Example:
```bash
curl -sS "$BASE_URL/api/v1/orders?status=waiting_sms" \
  -H "Authorization: Bearer $TOKEN"
```

### Cancel order

`POST /api/v1/orders/{public_id}/cancel`

Notes:
- Cancel refunds a held amount (if applicable) and transitions the order to `cancelled` when allowed.
- Some terminal statuses cannot be cancelled (returns `409`).

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/orders/$PUBLIC_ID/cancel" \
  -H "Authorization: Bearer $TOKEN"
```

### Finish order

`POST /api/v1/orders/{public_id}/finish`

Notes:
- Only allowed after SMS is received (`sms_received`), otherwise returns `409`.
- Finishing captures the hold and transitions to `completed`.

Example:
```bash
curl -sS -X POST "$BASE_URL/api/v1/orders/$PUBLIC_ID/finish" \
  -H "Authorization: Bearer $TOKEN"
```

## Common Errors / Patterns

The API uses JSON errors. Typical patterns:
- `401 {"detail":"Missing bearer token"}` or `{"detail":"Invalid token or API key"}`
- `403 {"detail":"..."}` for permission issues
- `404 {"detail":"..."}` for not found
- `409 {"detail":"..."}` for conflicts (invalid transitions, idempotency mismatch, etc.)
- `402` may be returned for insufficient wallet balance on purchase attempts
- `429 {"detail":"Rate limit exceeded"}`

Some internal services also return structured API errors with fields like:
- `{"error": {"code": "...", "message": "..."}}`

Client guidance:
- Treat all non-2xx as failures.
- On network timeout, you may retry `POST /api/v1/orders` with the same `Idempotency-Key` to avoid duplicate holds/orders.
